## 3. Notable decisions / gotchas (for the reviewer)

- **zod v4 migration.** BetterAuth requires zod ^4; the API was on zod v3. A
  v3/v4 split made `tsc` hang (pathological cross-version type relations via
  `@hono/zod-validator`). Fix: the API is now on **zod v4** (only change needed:
  `z.string().datetime()` → `z.iso.datetime()` in `bookings.ts` + `dogs.ts`).
- **`session` table collision.** The domain already owns `session`; BetterAuth's
  auth-session table is named **`auth_session`** at the SQL level (addressed by
  BetterAuth under its model key `session` via the explicit adapter `schema`).
- **Hand-authored auth schema.** `@better-auth/cli generate` depends on
  `better-sqlite3`, which won't build on this Windows toolchain, so
  `auth-schema.ts` was hand-authored to mirror BetterAuth 1.6.x's canonical core
  fields (cross-checked against `better-auth/dist/db` + the drizzle-adapter
  source). The SQL is still generated by `drizzle-kit`. **This is why §4 (a real
  sign-in against Postgres) is the key remaining check.**
- **Node/vitest caveat.** Fresh shells default to Node 16; `nvm use 20.20.2`
  repoints the symlink but flaps mid-command and hangs vitest worker spawn. Run
  tooling via the **absolute** Node 20 path
  (`~/AppData/Roaming/nvm/v20.20.2/node.exe`).

## 4. Pending manual step — live-DB sign-in smoke test

Not run here (no local Postgres; Docker engine was not started). This is the one
check that validates the hand-authored auth schema end-to-end. Steps:

```bash
# Postgres (Docker)
docker run --name tailsup-pg -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=tailsup -p 5432:5432 -d postgres:16
# .env: DATABASE_URL=postgresql://postgres:postgres@localhost:5432/tailsup
#       AUTH_SECRET=<openssl rand -base64 32>

npm run db:migrate -w apps/api     # applies 0000 + 0001_betterauth_tables
npm run db:seed    -w apps/api     # creates the two logins (see README)
npm run dev        -w apps/api

# Sign in as the trainer (expect HTTP 200 + a Set-Cookie session cookie):
curl -i -X POST http://localhost:3000/api/auth/sign-in/email \
  -H 'Content-Type: application/json' \
  -d '{ "email": "trainer@tailsup.local", "password": "Trainer123!" }'

# Reuse that cookie against a guarded route (expect 200 + the trainer's dogs):
curl -s http://localhost:3000/trainers/<seededTrainerId>/dogs -b 'better-auth.session_token=...'
```

Acceptance: sign-in returns 200 with a session; `getSession` resolves the user
with `role: "trainer"` and the linked `trainerId`; a guarded route returns the
trainer's data with the cookie and `401` without it. If any auth column is
rejected by BetterAuth at runtime, adjust `auth-schema.ts` and regenerate the
migration — but the schema is expected to be correct.
