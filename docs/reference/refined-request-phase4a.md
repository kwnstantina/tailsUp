## Category

Development

## Objective

Turn TailsUp's structured behaviour data into something the paying client can
actually read: a short, plain-language progress narrative for their dog,
generated by the trainer on demand from the logged `behavior_event` history, and
shown on the client dashboard above the existing threshold-over-time
`ProgressCurve`. Generation is metered against a monthly spend cap that warns
before it bites and cannot be exceeded.

The differentiator this serves: the structured `intervention → outcome` linkage
(the moat) is the one thing a generic AI dog-advice tool cannot produce. The
summary is grounded in that data, never in generic training advice.

## Scope

### In scope (Phase 4a — the deliverable)

1. **`POST /dogs/:id/summary`** — trainer-only. Computes a digest of the dog's
   behaviour history, calls Anthropic `claude-haiku-4-5`, stores the result
   (Greek **and** English) with its token counts and cost, returns it.
2. **`GET /dogs/:id/summary`** — trainer-only. The latest stored summary for that
   dog plus current month-to-date AI spend, so the trainer sees remaining budget
   before spending.
3. **`GET /me/summaries`** — client-only. The latest summary per dog the client
   owns, in one call (shaped like the existing `/me/progress`).
4. **Migration `0002_dog_summary`** — one new table, one new pgEnum, two indexes.
5. **`lib/summary-digest.ts`** — SQL/TS aggregation of a dog's behaviour history
   into a compact digest (not raw rows).
6. **`lib/anthropic.ts`** — lazily-configured Anthropic client, token counting,
   the structured-output call, response validation.
7. **`lib/ai-budget.ts`** — month-to-date spend, pre-flight hard stop, threshold
   warning email (through the existing `lib/email.ts`).
8. **New shared DTOs + enum** in `packages/shared` (pure TS, Metro-safe).
9. **Client dashboard summary card** (`apps/mobile/app/(app)/client.tsx`), above
   the existing `ProgressCurve`, bilingual off the existing i18n toggle.
10. **Trainer generate action** (`apps/mobile/app/(app)/dogs/[id]/timeline.tsx`)
    with last-generated date and remaining budget visible before the tap.
11. **Tests** — ~30 new API tests (mocked DB + mocked Anthropic SDK, suite stays
    credential-free), taking the API suite from 226 to ~256.
12. **Docs** — `.env.example` entries for the three new vars, README Phase 4a
    section, and an integration-verification report.

### Out of scope (explicitly NOT built in 4a)

- **Multi-tenant SaaS preparation** — this is **Phase 4b**, its own spec. No
  tenant column, no per-tenant billing, no signup flow, no tenant-scoped
  ownership refactor in 4a.
- **The locked visual redesign.** A separate brainstorming thread locked a bold
  editorial direction (`home-editorial-bold-v2`, with a DS-4/DS-6 amendment); its
  mockups live in `.superpowers/brainstorm/594-1785018351/content/` (gitignored)
  and its design doc and ordered plan were never written. 4a uses the **existing**
  `design_system.md` only. Mixing an unreviewed redesign into 4a would make 4a
  un-reviewable.
- **A trainer-facing clinical brief.** The summary in 4a is client-facing. A
  terse trainer-facing variant is a later addition once the prompt and cost
  profile are proven in real use.
- **Client-triggered generation.** Only the trainer can spend money in 4a.
- **Automatic/scheduled regeneration.** No background jobs, no cron, no
  regenerate-on-session-log.
- **Streaming the summary.** Output is ~700 tokens; a single non-streaming call
  is correct.
- **Prompt caching.** Not applicable at this prompt size (see D-4a-9).
- **A second AI feature of any kind.** The summary endpoint is deliberately the
  only Anthropic caller in 4a — the spend accounting depends on it (D-4a-4).

## Functional requirements

**FR-4a-1 — Generate a summary.** `POST /dogs/:id/summary` resolves the dog,
builds a digest of its behaviour history, calls `claude-haiku-4-5`, and persists
one `dog_summary` row containing the Greek text, the English text, the model id,
input/output token counts, computed cost in micro-USD, the event count the
summary was based on, and the generation timestamp. Returns `201` with the
created summary.

**FR-4a-2 — Trainer-only generation, ownership checked in the handler.** The
route inherits the mounted `app.use('/dogs/*', requireTrainer)` guard (401
unauthenticated, 403 for a client session). Ownership is then enforced **inside
the handler**: resolve `dog → client → client.trainerId` and compare it to the
session's `user.trainerId`; on mismatch return **404 `{ error: 'dog not found' }`**
(not 403 — a 403 would confirm that a dog id exists in another practice).

> **`requireTrainerOwnsParam` cannot be used here.** That middleware only compares
> against a **`trainerId` path param**, and `/dogs/:id/summary` has no such param —
> it would silently degrade to "any authenticated trainer". This is also a
> **pre-existing gap on the Phase 2 `/dogs/*` reads** (`GET /dogs/:id`,
> `/dogs/:id/timeline`), which perform no ownership check at all; see §12.

**FR-4a-3 — Bilingual in one call.** A single request returns both `summaryEl`
and `summaryEn` via structured output. Both are stored on the same row. The
client dashboard renders whichever matches the current i18n toggle, so a
language switch never produces an empty state and never triggers a second call.

**FR-4a-4 — Grounded digest, not raw rows.** The prompt is built from a computed
digest — event count, date span, weekly threshold trend, mean intensity,
outcome distribution, top interventions paired with their outcomes, trigger-type
breakdown, and the most recent notes — over the **last 180 days**, capped at the
**most recent 300 events**. Raw `behavior_event` rows are never dumped into the
prompt.

**FR-4a-5 — Minimum-data floor.** The endpoint returns `422` without calling
Anthropic and without writing a row when, in the digest window,
`eventCount < 5` **OR** `sessionCount < 2` (either condition alone is
disqualifying). There is nothing to summarise and no reason to spend.

**FR-4a-6 — Month-to-date spend.** Spend for the current UTC calendar month is
`SUM(cost_micros)` over `dog_summary` rows with `generated_at >=` the start of
that month, **including** rows with `status = 'failed'` (a failed call that
consumed tokens still cost money).

**FR-4a-7 — Pre-flight hard stop.** Before calling Anthropic, the endpoint counts
the digest's real input tokens via `messages.countTokens()` and computes the
worst-case cost of the call (`estimatedInputTokens × 1 + max_tokens × 5` micros).
If `spent + worstCase > budget`, it returns `429` **without calling Anthropic**.
The cap can therefore be reached but never exceeded.

**FR-4a-8 — Threshold warning.** After the insert, if month-to-date spend crossed
the warn threshold on this call (`spentBefore < threshold && spentAfter >=
threshold`), one warning email is sent **fire-and-forget** through the existing
`lib/email.ts`. Recipient: the `trainer.email` of the trainer who owns the dog
(the session's `user.trainerId`), not `resolveTrainerId()` — the owner is already
known from the ownership check in FR-4a-2. A Resend failure, a missing
`RESEND_API_KEY`, or a slow send can never fail or delay the response.

**FR-4a-9 — Failed calls are recorded.** A refusal, a truncated response, an
invalid structured output, or an SDK/API error **that consumed tokens** writes a
`dog_summary` row with `status = 'failed'`, the token counts and cost known at
that point, and an `error_reason` (`refusal` | `max_tokens` | `invalid_output` |
`api_error`), then returns `502`. Failed rows carry `null` text and are never
served to a reader. An error where the call never reached the model (connection
failure, 401) records `0` tokens and `0` cost — the row exists for auditability,
contributing nothing to spend.

**FR-4a-10 — Never fabricate.** When `ANTHROPIC_API_KEY` is absent or blank the
endpoint returns `503`. There is no stub summary. (This inverts the `email.ts`
stub-and-succeed precedent and follows `r2.ts`'s throw-to-503 instead — see
D-4a-3.)

**FR-4a-11 — Trainer read + budget visibility.** `GET /dogs/:id/summary` returns
the latest `status = 'ok'` summary for that dog (or `summary: null` when none
exists) together with `{ spentMicros, budgetMicros, warnPercent }`.

**FR-4a-12 — Client read, scoped.** `GET /me/summaries` returns the latest
`status = 'ok'` summary for each dog belonging to the authenticated client, one
per dog. It returns **no budget or cost data** — the practice's AI spend is not
the client's business.

**FR-4a-13 — Client dashboard card.** The client dashboard renders the summary
card directly above the existing `ProgressCurve`, footed with the generation date
and the event count it was based on. With no summary yet it shows one quiet
bilingual line, not an error.

**FR-4a-14 — Trainer generate UI.** The dog timeline screen gains a "Generate
summary" action showing the last-generated date and the remaining monthly budget
before the tap. Past the warn threshold the action gains a confirm step.

**FR-4a-15 — Shared source of truth.** The summary status values live in
`packages/shared/src/enums.ts` as an `as const` array and back both the pgEnum
and the API's zod validation (the FR-9 one-source rule the existing six enums
follow). `packages/shared` stays pure TS with zero server imports.

## Non-functional requirements

**NFR-4a-1 — Low cost is priority #1.** Per-summary cost must stay well under one
cent, and no code path may start a call it cannot afford (FR-4a-7).

**NFR-4a-2 — Credential-free test suite.** The whole suite must pass with no
`ANTHROPIC_API_KEY`, no `DATABASE_URL`, no `RESEND_API_KEY`, and no network — the
Anthropic SDK and the DB are both mocked, matching the existing R2 and Resend
suites.

**NFR-4a-3 — No config fallbacks for secrets.** `ANTHROPIC_API_KEY` is read
lazily at call time and stays out of `config.ts` (so a keyless deploy still
boots and serves every non-AI route), exactly like `R2_*` and `RESEND_API_KEY`.

**NFR-4a-4 — TS strict, zero errors, all three workspaces.**

**NFR-4a-5 — Secrets hygiene.** `.env.example` gains placeholder entries only. No
key, no budget value from a real account, is committed.

**NFR-4a-6 — Design System fidelity.** Existing `design_system.md` tokens only;
Fraunces headings / Inter body; copper as accent, never a large surface; visible
focus on every interactive element; reduced motion respected; bilingual copy in
per-page `copy = { el, en }` objects.

## Technical design

### §1 Architecture

```
apps/mobile (app)/client.tsx ──GET /me/summaries──┐
   summary card above ProgressCurve               │
                                                  ▼
apps/mobile (app)/dogs/[id]/timeline.tsx ──▶ apps/api routes/summary.ts
   trainer "Generate summary" action         │
                                             ├─ lib/summary-digest.ts  (SQL → digest)
                                             ├─ lib/ai-budget.ts       (spend, cap, warn)
                                             ├─ lib/anthropic.ts       (lazy client, call)
                                             └─ lib/email.ts           (existing, F&F warn)
                                                          │
                                             INSERT dog_summary (text + tokens + cost)
```

`routes/summary.ts` is a new file rather than an addition to `dogs.ts`: `dogs.ts`
is already the read-heavy route file, and a route that spends money earns its own
test file. This matches the existing one-concern-per-route-file layout. It mounts
at `/` like every other route module (`app.route('/', summary)`), with full paths
declared inside.

### §2 Data model — migration `0002_dog_summary`

Table name singular; TS keys camelCase mapped to snake_case by the existing
`casing: 'snake_case'` client option; UUID PK with `defaultRandom()`; timestamps
`timestamptz`. All per Phase 1 conventions.

**`dog_summary`**

| TS key → column | PG type | Notes |
| --- | --- | --- |
| id → id | uuid PK | `defaultRandom()` |
| dogId → dog_id | uuid | FK → `dog.id` |
| textEl → text_el | text **N** | null **only** when `status='failed'` |
| textEn → text_en | text **N** | null **only** when `status='failed'` |
| status → status | `summary_status` enum | `ok` \| `failed` |
| errorReason → error_reason | text **N** | set only when `status='failed'` |
| model → model | text | e.g. `claude-haiku-4-5` — recorded per row so a future model or price change stays auditable |
| inputTokens → input_tokens | integer | from `response.usage.input_tokens` |
| outputTokens → output_tokens | integer | from `response.usage.output_tokens` |
| costMicros → cost_micros | integer | micro-USD; integer arithmetic (§5) |
| eventCount → event_count | integer | events in the digest window at generation time |
| generatedAt → generated_at | timestamptz | `defaultNow()` |

**Indexes (2):**

| Index name | Definition | Purpose |
| --- | --- | --- |
| `dog_summary_dog_generated_idx` | `(dog_id, generated_at)` | latest summary per dog |
| `dog_summary_generated_idx` | `(generated_at)` | month-to-date spend sum |

**Enum:** `summaryStatusEnum` → DB type `summary_status`, values from
`SUMMARY_STATUSES` in `@tailsup/shared`.

**`error_reason` is `text`, not an enum, on purpose.** Its documented values are
`refusal` | `max_tokens` | `invalid_output` | `api_error`, exported from shared as
`SUMMARY_ERROR_REASONS` for validation and typing — but keeping the column as
`text` means adding a fifth reason later is a code change, not a migration.

**Invariant:** `status='ok'` ⇒ `text_el` and `text_en` both non-null and non-empty,
`error_reason` null. `status='failed'` ⇒ both texts null, `error_reason` set.
Enforced in the insert path and asserted in tests (not as a DB CHECK constraint —
the repo has no CHECK-constraint precedent and the write path is single).

### §3 Shared contract additions (`packages/shared`)

```ts
// enums.ts
export const SUMMARY_STATUSES = ['ok', 'failed'] as const;
export type SummaryStatus = (typeof SUMMARY_STATUSES)[number];

export const SUMMARY_ERROR_REASONS = [
  'refusal', 'max_tokens', 'invalid_output', 'api_error',
] as const;
export type SummaryErrorReason = (typeof SUMMARY_ERROR_REASONS)[number];

// dtos.ts
export interface DogSummaryDTO {
  id: string;
  dogId: string;
  summaryEl: string;      // never empty — failed rows are never served
  summaryEn: string;
  eventCount: number;
  generatedAt: string;    // ISO
}

export interface AiBudgetDTO {
  spentMicros: number;
  budgetMicros: number;
  warnPercent: number;
}

// GET/POST /dogs/:id/summary (trainer) — includes budget
export interface TrainerDogSummaryDTO {
  summary: DogSummaryDTO | null;
  budget: AiBudgetDTO;
}

// GET /me/summaries (client) — NO cost data
export interface ClientSummariesDTO {
  summaries: DogSummaryDTO[];   // latest ok summary per owned dog
}
```

`model`, token counts, `costMicros`, `status`, and `errorReason` are deliberately
**absent** from every DTO. They are internal accounting, not wire contract.

### §4 API contracts

**`POST /dogs/:id/summary`** — mounted `requireTrainer` + in-handler ownership
check (FR-4a-2). No request body.

| Status | When | Body |
| --- | --- | --- |
| 201 | generated | `TrainerDogSummaryDTO` (summary non-null) |
| 401 | unauthenticated | `{ error: 'unauthorized' }` (from `requireTrainer`) |
| 403 | authenticated as a client | `{ error: 'forbidden' }` (from `requireTrainer`) |
| 404 | dog not found, or owned by another trainer | `{ error: 'dog not found' }` |
| 422 | below the minimum-data floor | `{ error: 'not enough behaviour data to summarise' }` |
| 429 | monthly AI budget reached | `{ error: 'ai budget exceeded', spentMicros, budgetMicros }` |
| 502 | refusal / truncated / invalid output / API error | `{ error: 'summary generation failed', reason }` |
| 503 | `ANTHROPIC_API_KEY` unconfigured | `{ error: 'ai not configured' }` |

**`GET /dogs/:id/summary`** — mounted `requireTrainer` + the same in-handler
ownership check. `200` with `TrainerDogSummaryDTO` (`summary: null` when none);
`401`/`403` as above; `404` when the dog is not found or owned by another
trainer. Never `503` — a keyless practice can still read history and its budget.

**`GET /me/summaries`** — `requireClient`. `200` with `ClientSummariesDTO`
(possibly an empty array).

**Status-code rationale.** `503` means *this practice has not configured AI*;
`429` means *configured fine, quota spent* — and `429` already carries "quota" in
this API (the `hono-rate-limiter` on `/leads` and `/bookings`). `502` says the
upstream model failed rather than that the request was wrong. `422` distinguishes
"nothing to summarise" from a malformed request (`400`).

### §5 Cost and budget arithmetic (`lib/ai-budget.ts`)

Haiku 4.5 pricing converts to exact integers, which is why no floats are needed:

> **$1 per 1M input tokens = 1 micro-USD per input token**
> **$5 per 1M output tokens = 5 micro-USD per output token**
>
> `costMicros = inputTokens × 1 + outputTokens × 5`

Constants live in `lib/ai-budget.ts` next to a comment recording that they are
`claude-haiku-4-5` rates verified 2026-07-26, and that `dog_summary.model` exists
so historical rows stay attributable if the rate or model changes.

**Realistic per-summary cost:** ~1,500 input + ~700 output tokens (both
languages) = 1,500 + 3,500 = **5,000 micros ≈ $0.005**. The default $5.00 monthly
budget is therefore roughly **1,000 summaries** — far beyond what one practice
generates by hand.

**Worst-case pre-flight cost:** `estimatedInputTokens × 1 + 1200 × 5` micros
(`1200` = `max_tokens`). For a typical digest that is ~7,500 micros ≈ $0.0075.

**Three mechanics:**

1. **Month-to-date** — `SUM(cost_micros)` where `generated_at >=` start of the
   current **UTC** calendar month, all statuses included.
2. **Pre-flight hard stop** — FR-4a-7. Returns `429` before any Anthropic call.
3. **Warn on crossing** — FR-4a-8. The crossing test
   (`spentBefore < threshold && spentAfter >= threshold`) is self-idempotent:
   there is no "already warned" flag to persist, and it resets naturally at the
   month boundary because `spentBefore` returns to 0.

**Config, read lazily alongside the API key (out of `config.ts`):**

| Var | Default | Notes |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | none | absent ⇒ `503` on generate; every other route unaffected |
| `AI_MONTHLY_BUDGET_MICROS` | `5000000` ($5.00) | see below |
| `AI_WARN_PERCENT` | `80` | integer percent |

The budget default is a deliberate reading of the project's no-config-fallbacks
rule. That rule exists so nothing runs on a silent default; here the *dangerous*
default is **unlimited**, so a missing budget fails **safe** (a low cap) rather
than open. Both defaults are documented in `.env.example`.

### §6 The digest (`lib/summary-digest.ts`)

Window: events in the **last 180 days**, capped at the **most recent 300**.
Computed fields fed to the model:

- dog: name, breed, age in months, background notes (if any), protocol name and
  its default intervention
- coverage: event count, session count, first and last event dates
- threshold trend: mean `thresholdMeters` per ISO week across the window
- intensity: mean and trend of `intensity`
- outcomes: counts of `disengaged` / `recovered_slowly` / `over_threshold`
- **interventions paired with their outcomes** — the moat; the single most
  important input, and what makes the output non-generic
- triggers: counts by `triggerType`
- recent notes: the most recent handful of non-empty `note` values

Two queries (dog+protocol, then events), following the existing no-N+1 pattern in
`dogs.ts`/`me.ts` — plain `select()` with joins and `inArray` batching, no
`relations()`.

**Untrusted text is fenced.** `note` and `tags` are trainer-entered free text that
reaches a client-visible output. They are passed as clearly-delimited quoted
material, never concatenated into the instruction portion of the prompt. The
trainer is a trusted user; this is defence-in-depth, the same posture as the
`escapeHtml` hardening already applied in `lib/email.ts`.

### §7 The model call (`lib/anthropic.ts`)

#### 7.1 Shape

```
countTokens(digest) → budget pre-flight → messages.create → stop_reason checks
  → zod validation → INSERT → (maybe) warn email → 201
```

Lazy client, mirroring `email.ts`'s cached-client shape but with `r2.ts`'s
throw-on-missing behaviour:

```ts
let client: Anthropic | null = null;
function getClient(): Anthropic {
  const key = process.env.ANTHROPIC_API_KEY;
  if (!key || key.trim() === '') throw new AiNotConfiguredError();
  client ??= new Anthropic({ apiKey: key });
  return client;
}
```

#### 7.2 Request parameters — and the Haiku-4.5 constraints

| Parameter | Value | Why |
| --- | --- | --- |
| `model` | `claude-haiku-4-5` | The decided stack. $1/$5 per MTok, 200K context. |
| `max_tokens` | `1200` | Two short paragraphs × two languages. Deliberately low as a cost ceiling; truncation is detected, not ignored. |
| `system` | practice/summary instructions | Stable; short. |
| `output_config.format` | `json_schema`, **raw JSON Schema** | Structured output is supported on Haiku 4.5. Guarantees `{ summaryEl, summaryEn }` rather than prose-wrapped JSON. |
| `output_config.effort` | **omitted** | `effort` is **rejected on Haiku 4.5** — sending it is an error, not a no-op. |
| `thinking` | **omitted** | Haiku 4.5 does not think unless asked. A digest summary does not need it, and it would inflate the bill. |
| `cache_control` | **omitted** | See D-4a-9. |
| `temperature` | **omitted** | Not needed; prompt-steered. |

**Deliberate deviation — raw JSON Schema, not the SDK's `zodOutputFormat` helper.**
`apps/api` runs `zod@^4.4.3`, and Phase 3b-1 already lost time to a zod v3/v4
split (a mixed install hung `tsc`). The schema is therefore sent as plain JSON
Schema, and the returned object is validated with the project's own zod v4 after
the call. Same guarantee, no coupling to the SDK helper's zod-version support.

#### 7.3 Response handling, in order

1. **`stop_reason === 'refusal'`** → `failed` row, `error_reason='refusal'`, `502`.
   Checked **first**: indexing `content[0]` on a refusal throws.
2. **`stop_reason === 'max_tokens'`** → the structured JSON is truncated and
   unparseable → `failed` row, `error_reason='max_tokens'`, `502`.
3. **Parse + zod-validate** the structured output. Failure → `failed` row,
   `error_reason='invalid_output'`, `502`.
4. **Success** → `ok` row, `201`.

Token counts always come from `response.usage`. Pre-flight estimation uses
`client.messages.countTokens()` — never a `tiktoken`-style approximation, which
undercounts Claude by 15–20% and would make the cap unreliable.

SDK errors are caught with the SDK's **typed** exception classes in a
most-specific-first chain (`RateLimitError` → `APIStatusError` →
`APIConnectionError` → `APIError`), never by string-matching messages. Any of
them → `failed` row with the tokens known so far (0 if the call never landed),
`error_reason='api_error'`, `502`.

### §8 Mobile

**Client dashboard** (`apps/mobile/app/(app)/client.tsx`) — summary card directly
above the existing `ProgressCurve`. Renders `summaryEl`/`summaryEn` off the
existing i18n context. Footer: "Updated {date} · based on {n} logged events". No
summary → one quiet bilingual line ("Your trainer hasn't shared a summary yet"),
not an error state.

**Trainer** (`apps/mobile/app/(app)/dogs/[id]/timeline.tsx`) — "Generate summary"
action plus the last-generated date and remaining monthly budget, shown **before**
the tap. Past `AI_WARN_PERCENT`, the action gains a confirm step; below it, one
tap. Spending should be visible, not interrogated every time.

Existing Design System only (NFR-4a-6). Not the `home-editorial-bold-v2`
direction.

### §9 Error-handling summary

- Missing key → `503`, no row, nothing fabricated (FR-4a-10).
- Below floor → `422`, no spend, no row (FR-4a-5).
- Over budget → `429`, no Anthropic call (FR-4a-7).
- Consumed tokens but no usable output → `failed` row + `502` (FR-4a-9).
- Warning email may fail freely; the `201` is unaffected (FR-4a-8).
- `GET` paths never 500 on absence — `summary: null` or an empty array.

### §10 Testing

Vitest; DB **and** the Anthropic SDK both mocked (NFR-4a-2). ~30 new tests across
`summary.test.ts`, `ai-budget.test.ts`, and `summary-digest.test.ts`. The ones
that carry weight:

1. **429 pre-flight asserts the Anthropic mock recorded zero calls** — the entire
   cap rests on this one assertion.
2. Cost arithmetic exact against known token counts (`in×1 + out×5`).
3. `refusal` and `max_tokens` each write a `failed` row whose cost still counts
   toward month-to-date spend.
4. Warn email fires exactly once on the crossing call, not on the next; a
   rejecting email mock still yields `201`.
5. Role guards: client cannot POST; trainer cannot summarise another trainer's
   dog; `/me/summaries` is client-scoped and cost-free.
6. `422` floor fires before any spend.
7. Digest aggregation: weekly threshold means, outcome counts, and
   intervention→outcome pairing computed correctly from a fixture history.

### §11 Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| **D-4a-1** | **Split Phase 4 into 4a (AI) and 4b (multi-tenant)** | Multi-tenancy touches every table, the auth↔domain link, and every ownership check; the AI work is one route and one table. Same reasoning that split 3a/3b and 3b-1/3b-2. Keeps the migration-heavy work behind its own review gate. |
| **D-4a-2** | **Client-facing narrative** (not a trainer clinical brief) | Highest product value: it turns the structured data into something the paying client feels, above the `ProgressCurve` they already see. A trainer variant can follow once prompt and cost are proven. |
| **D-4a-3** | **Missing key ⇒ 503, never a stub** | A fabricated progress report shown to a paying client is the worst failure mode in this feature. Follows `r2.ts` (throw → 503) rather than `email.ts` (stub and succeed) — a stubbed email is invisible, a stubbed summary is a lie. |
| **D-4a-4** | **Cost columns on `dog_summary`; no separate `ai_usage` ledger** | The summary endpoint is the only Anthropic caller in 4a, so call and row are 1:1 — a ledger would be a second copy of the same facts. One table, full audit trail, and `status='failed'` keeps billed-but-useless calls counted. Extractable into a ledger later without data loss if a second AI feature lands. |
| **D-4a-5** | **Trainer-triggered only; client reads the stored row** | Only the practice owner can spend the practice's money. No client-driven cost, no client-facing rate limiter, and the trainer controls what the client reads. |
| **D-4a-6** | **Both languages in one call** | One request, ~2× output tokens (still ≈half a cent), both columns stored. A language toggle never produces an empty state or a second spend event. |
| **D-4a-7** | **Warn at threshold *and* hard-stop at cap** | "Low maintenance, low cost" is priority #1 and this is a solo project — a reminder alone cannot stop a runaway loop overnight. The pre-flight check (FR-4a-7) makes the cap unbreachable rather than merely observed. |
| **D-4a-8** | **Digest, not raw rows** | ~10× fewer input tokens, and it grounds the model in the aggregate the client cares about instead of letting it re-derive statistics from 300 rows and get them wrong. |
| **D-4a-9** | **No prompt caching** | Haiku 4.5's minimum cacheable prefix is **4096 tokens**; the system prompt is far below it, so a `cache_control` breakpoint would silently never cache — paying the ~1.25× write premium for zero reads. |
| **D-4a-10** | **Raw JSON Schema over the SDK's zod helper** | `apps/api` is on zod v4 and a v3/v4 split already hung `tsc` in Phase 3b-1. Structured output is still guaranteed; validation uses the project's own zod. |
| **D-4a-11** | **Budget default is a conservative cap, not unlimited** | The no-fallbacks rule exists so nothing runs on a silent default. Here the dangerous default is unlimited, so a missing budget fails safe at $5.00. |
| **D-4a-12** | **`error_reason` is `text`, not a pgEnum** | Adding a fifth failure reason later becomes a code change instead of a migration. Its valid values still live in shared for typing and validation. |
| **D-4a-13** | **`routes/summary.ts` is a new file** | `dogs.ts` is already the read-heavy route file; a money-spending route earns its own test file. Matches the one-concern-per-route-file layout. |
| **D-4a-14** | **UTC calendar month for the budget period** | Unambiguous, matches `timestamptz` storage, and needs no practice-timezone config in 4a. |

### §12 Known-pending

**NEW FINDING (surfaced while writing this spec) — pre-existing cross-trainer read
gap on the Phase 2 `/dogs/*` routes.** `app.ts:90` mounts
`app.use('/dogs/*', requireTrainer)`, which only proves *a* trainer is signed in.
`GET /dogs/:id`, `GET /dogs/:id/timeline`, and `POST /dogs/:id/sessions` then look
the dog up **by id alone**, with no `dog → client → trainerId` comparison — so any
authenticated trainer can read (and start a session on) any dog in the database,
given its id. `requireTrainerOwnsParam` does not cover these routes because it
keys off a `trainerId` path param that they do not have.

- **Impact today: latent.** The practice is single-trainer, so there is no second
  trainer to exploit it.
- **Impact at 4b: live vulnerability.** Multi-tenancy makes this cross-tenant data
  disclosure, so it is a **hard prerequisite for Phase 4b**, not a nice-to-have.
- **4a's own endpoints do not inherit it** — FR-4a-2 specifies the in-handler
  ownership check for all three new routes.
- **Not fixed in 4a as specified.** Retrofitting the three Phase 2 routes is a
  small change (one shared `assertTrainerOwnsDog()` helper plus tests) but it is
  outside the requested Phase 4a scope and touches Phase 2 behaviour, so it is the
  user's call whether to fold it in here or hold it for 4b. Recorded in
  `Issues - Pending Items.md` either way.

**Carried from earlier phases (not introduced here):**

- **Live-DB walkthrough still pending from 3b-1/3b-2** (needs Docker Postgres).
  Phase 4a adds the first migration since `0001`, so that walkthrough now also
  covers `0002_dog_summary` applying on top of `0001`.
- **A one-off live Anthropic call** is needed to confirm the real
  `response.usage` numbers match the cost arithmetic in §5. Mocked tests prove
  the arithmetic; only a live call proves the field mapping.
- **Deferred dependency advisories** (Expo SDK 54 transitive; `drizzle-kit` →
  `esbuild@~0.18`) remain deferred. Phase 4a adds exactly one runtime dependency,
  `@anthropic-ai/sdk`, to `apps/api` only — it must not enter the mobile bundle.
